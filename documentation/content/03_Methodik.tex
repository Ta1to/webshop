\chapter{Methodik}
\label{ch:methodik}

Dieses Kapitel beschreibt das methodische Vorgehen bei der Entwicklung des Webshops. Es werden das gewählte Vorgehensmodell, die durchgeführte Anforderungsanalyse sowie die daraus resultierende Konzeption und Architektur der Anwendung vorgestellt.

\section{Vorgehensmodell}
\label{sec:vorgehensmodell}

\subsection{Auswahl des Vorgehensmodells}
\label{subsec:vorgehensmodell-auswahl}

Für die Entwicklung des Webshops wurde ein iterativ-inkrementelles Vorgehensmodell gewählt, das Elemente aus agilen Methoden mit einer strukturierten Projektplanung kombiniert. Diese Entscheidung basiert auf mehreren Faktoren:

\textbf{Projektcharakteristik:} Als Studienarbeit mit definiertem Zeitrahmen und bekanntem Funktionsumfang eignet sich ein hybrides Vorgehen, das Flexibilität bei gleichzeitiger Planbarkeit bietet.

\textbf{Teamgröße:} Mit zwei Entwicklern ist ein schlankes Vorgehensmodell ohne übermäßigen Verwaltungsaufwand sinnvoll.

\textbf{Technologische Unsicherheit:} Die Verwendung von Firebase als relativ neuer Technologie erfordert Raum für Experimente und iterative Verbesserungen.

\textbf{Anforderungsstabilität:} Die grundlegenden Anforderungen an einen Webshop sind etabliert und stabil, was längerfristige Planung ermöglicht.

\subsection{Entwicklungspraktiken}
\label{subsec:entwicklungspraktiken}

Im Rahmen des Projekts wurden verschiedene Entwicklungspraktiken angewendet:

\textbf{Versionskontrolle:} Der gesamte Quellcode wird in einem Git-Repository verwaltet. Dies ermöglicht die Nachverfolgung von Änderungen, parallele Entwicklung durch Branching und die Möglichkeit, auf frühere Versionen zurückzugreifen \cite{chacon2014}.

\textbf{Kontinuierliche Integration:} Änderungen werden regelmäßig in den Hauptentwicklungszweig integriert und automatisch gebaut. Dies ermöglicht die frühzeitige Erkennung von Integrationsproblemen.

\textbf{Code-Reviews:} Vor der Integration in den Hauptzweig werden Änderungen von beiden Teammitgliedern geprüft. Dies verbessert die Codequalität und fördert den Wissensaustausch.

\textbf{Dokumentation:} Relevante Entscheidungen und Implementierungsdetails werden fortlaufend dokumentiert. Dies umfasst sowohl Inline-Kommentare im Code als auch separate Dokumentation für komplexere Konzepte.

\subsection{Abgrenzung}
\label{subsec:abgrenzung}

Zur Eingrenzung des Projektumfangs wurden bewusst bestimmte Funktionalitäten ausgeschlossen:

\begin{itemize}
    \item \textbf{Echte Zahlungsabwicklung:} Die Integration eines Zahlungsdienstleisters wie PayPal oder Stripe ist nicht Teil des Prototyps. Der Checkout-Prozess simuliert die Zahlungserfassung.
    
    \item \textbf{Versandintegration:} Eine Anbindung an Versanddienstleister zur Sendungsverfolgung ist nicht vorgesehen.
    
    \item \textbf{Mehrsprachigkeit:} Die Anwendung wird ausschließlich in deutscher Sprache entwickelt.
    
    \item \textbf{Produktbewertungen:} Ein System für Kundenbewertungen und -rezensionen ist nicht Teil des Projektumfangs.
    
    \item \textbf{Newsletter:} Eine Newsletter-Funktionalität mit E-Mail-Marketing ist nicht vorgesehen.
\end{itemize}

Diese Abgrenzungen ermöglichen die Fokussierung auf die Kernfunktionalitäten eines E-Commerce-Systems im gegebenen Zeitrahmen.

\section{Konzeption und Architektur}
\label{sec:konzeption-architektur}

Basierend auf den erhobenen Anforderungen wurde die Architektur des Webshops konzipiert. Dieser Abschnitt beschreibt die gewählte Systemarchitektur, die Datenbankstruktur und die Komponentenarchitektur des Frontends.

\subsection{Systemarchitektur}
\label{subsec:systemarchitektur}

Die Anwendung folgt einer Client-Server-Architektur, bei der das Frontend als Single Page Application im Browser des Benutzers ausgeführt wird und über APIs mit den Firebase-Backend-Diensten kommuniziert.

Die Architektur zeichnet sich durch folgende Merkmale aus:

\textbf{Lose Kopplung:} Frontend und Backend-Dienste kommunizieren ausschließlich über definierte APIs. Dies ermöglicht unabhängige Weiterentwicklung und einfachen Austausch einzelner Komponenten.

\textbf{Zustandslosigkeit:} Der Server speichert keinen Client-Zustand zwischen Anfragen. Session-Informationen werden im Client verwaltet, Authentifizierungstoken werden bei jeder Anfrage mitgesendet.

\textbf{Ereignisgesteuert:} Änderungen in der Datenbank können Cloud Functions auslösen, die serverseitige Logik ausführen. Dies ermöglicht reaktive Verarbeitung ohne aktives Polling.

\subsection{Datenbankstruktur}
\label{subsec:datenbankstruktur}

Cloud Firestore organisiert Daten in Dokumenten und Collections. Für den Webshop wurden folgende Haupt-Collections definiert:

\textbf{users:} Speichert Benutzerdaten wie Name, E-Mail, Adresse und Rolle. Die Dokument-ID entspricht der Firebase Auth UID.

\textbf{products:} Enthält alle Produktinformationen einschließlich Name, Beschreibung, Preis, Kategorie und Lagerbestand. Produktbilder werden als URLs zu Firebase Storage gespeichert.

\textbf{categories:} Definiert die verfügbaren Produktkategorien mit Name und optionaler Beschreibung.

\textbf{orders:} Speichert Bestellungen mit Referenz zum Benutzer, bestellten Produkten, Gesamtbetrag, Lieferadresse und Bestellstatus.

\textbf{offers:} Enthält Sonderangebote mit Gültigkeitszeitraum, Rabatttyp und -höhe sowie Referenzen zu betroffenen Produkten.

\subsection{Frontend-Komponentenarchitektur}
\label{subsec:komponentenarchitektur}

Das Frontend ist nach dem Komponentenprinzip von Vue.js strukturiert. Die Komponenten sind hierarchisch organisiert und nach ihrer Funktion gruppiert:

\textbf{Views:} Seitenkomponenten, die über den Router angesteuert werden. Sie entsprechen den Hauptseiten der Anwendung wie Startseite, Produktübersicht oder Checkout.

\textbf{Layout-Komponenten:} Strukturelle Komponenten wie Header, Footer und Navigation, die auf mehreren Seiten verwendet werden.

\textbf{Feature-Komponenten:} Fachliche Komponenten wie Produktkarte, Warenkorb-Dialog oder Bestellübersicht, die spezifische Funktionalitäten kapseln.

\textbf{Utility-Komponenten:} Wiederverwendbare UI-Elemente wie Buttons, Eingabefelder oder Benachrichtigungen.

Die Kommunikation zwischen Komponenten erfolgt über:

\begin{itemize}
    \item \textbf{Props:} Datenübergabe von Eltern- an Kind-Komponenten
    \item \textbf{Events:} Kommunikation von Kind- zu Eltern-Komponenten
    \item \textbf{Stores:} Zentraler Zustand für komponentenübergreifende Daten (Pinia)
\end{itemize}

\subsection{Sicherheitskonzept}
\label{subsec:sicherheitskonzept}

Die Sicherheit der Anwendung basiert auf mehreren Ebenen:

\textbf{Authentifizierung:} Firebase Authentication verwaltet die Benutzeridentität. Bei erfolgreicher Anmeldung erhält der Client ein JWT-Token, das bei allen Backend-Anfragen mitgesendet wird.

\textbf{Autorisierung:} Firestore Security Rules definieren, welche Benutzer auf welche Daten zugreifen dürfen. Beispielsweise können Benutzer nur ihre eigenen Bestellungen lesen, während Administratoren Zugriff auf alle Daten haben.

\textbf{Datenverschlüsselung:} Alle Kommunikation zwischen Client und Firebase erfolgt über HTTPS. Firebase verschlüsselt gespeicherte Daten automatisch.

\textbf{Input-Validierung:} Benutzereingaben werden sowohl im Frontend als auch durch Security Rules im Backend validiert, um Injection-Angriffe zu verhindern.

Ein Beispiel für Firestore Security Rules:

\begin{lstlisting}[language=Java, caption=Firestore Security Rules (Auszug)]
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    // Benutzer koennen nur eigene Daten lesen/schreiben
    match /users/{userId} {
      allow read, write: if request.auth != null 
                         && request.auth.uid == userId;
    }
    
    // Produkte sind oeffentlich lesbar
    match /products/{productId} {
      allow read: if true;
      allow write: if isAdmin();
    }
    
    // Hilfsfunktion zur Admin-Pruefung
    function isAdmin() {
      return request.auth != null 
             && get(/databases/$(database)/documents/users/$(request.auth.uid)).data.role == 'admin';
    }
  }
}
\end{lstlisting}

\subsection{Deployment-Konzept}
\label{subsec:deployment-konzept}

Das Deployment der Anwendung erfolgt über Firebase Hosting mit automatisierter CI/CD-Pipeline:

\begin{enumerate}
    \item \textbf{Build:} Der Vue.js-Quellcode wird durch Vite zu optimierten statischen Dateien kompiliert.
    \item \textbf{Test:} Automatisierte Tests prüfen die Funktionalität der Anwendung.
    \item \textbf{Deploy:} Die Build-Artefakte werden zu Firebase Hosting hochgeladen.
    \item \textbf{Aktivierung:} Firebase aktiviert die neue Version und routet Traffic automatisch um.
\end{enumerate}

Firebase Hosting bietet dabei Features wie automatische SSL-Zertifikate, globales CDN und atomare Deployments mit Rollback-Möglichkeit.
