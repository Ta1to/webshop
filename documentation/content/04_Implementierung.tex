\chapter{Implementierung}
\label{ch:implementierung}

Dieses Kapitel dokumentiert die technische Umsetzung des Webshops anhand der architektonisch bedeutsamen Entwurfsentscheidungen und zentralen Implementierungsmuster. Rein technische Details ohne konzeptionellen Mehrwert werden dabei ausgeklammert.

\section{Projektstruktur und Frontend-Gerüst}
\label{sec:projektstruktur}

Als Build-Tool kommt Vite zum Einsatz. Gegenüber klassischen Bundlern bietet Vite einen nativen ES-Module-Dev-Server, der Module erst bei Bedarf transformiert und damit nahezu sofortige Startzeiten sowie reaktives Hot Module Replacement erreicht \cite{vite2025}. Produktionsbuilds werden über Rollup mit Tree-Shaking und automatischem Code-Splitting erzeugt.

Die Verzeichnisstruktur orientiert sich am Feature-orientierten Prinzip und trennt klar nach Verantwortlichkeiten: \texttt{views/} enthält die den Routen zugeordneten Seitenkomponenten, \texttt{components/} die kontextbezogen untergliederten UI-Bausteine, \texttt{services/} die zweischichtige Serviceschicht aus Firebase-SDK-Abstraktion (\texttt{firebase/}) und Domänenlogik (\texttt{business/}), sowie \texttt{models/} die Domänenmodelle mit eingebetteter Validierungslogik. Diese Gliederung nach fachlicher Verantwortlichkeit verbessert Testbarkeit und reduziert strukturelle Kopplung \cite{kothapalli2021, kothapalli2022}.

Das Routing ist über Vue Router mit \texttt{createWebHistory()} realisiert. Schutzbedürftige Routen werden über die Metafelder \texttt{requiresAuth} und \texttt{requiresAdmin} deklarativ markiert und zur Laufzeit durch einen globalen Navigation Guard ausgewertet.

\section{Integration von Firebase-Diensten}
\label{sec:firebase-integration}

Sämtliche Firebase-Verbindungsparameter werden über Vite-Umgebungsvariablen eingelesen -- kein Credential ist im Quellcode hart kodiert. Dies verhindert die unbeabsichtigte Exponierung von API-Schlüsseln im Versionskontrollsystem und entspricht einer grundlegenden Sicherheitsempfehlung für Web-Anwendungen \cite{fredj2020}:

\begin{lstlisting}[language=Java, morekeywords={const, export}, caption=Firebase-Konfiguration über Umgebungsvariablen (config.js)]
const firebaseConfig = {
  apiKey:    import.meta.env.VITE_FIREBASE_API_KEY,
  projectId: import.meta.env.VITE_FIREBASE_PROJECT_ID,
  // ...weitere Parameter
}
export const { db, auth, storage } = initFirebase(firebaseConfig)
\end{lstlisting}

Die Datenbankschicht (\texttt{db.js}) implementiert ein generisches CRUD-Muster: Fünf universelle Funktionen abstrahieren den Firestore-Zugriff collectionübergreifend. Jeder Schreibvorgang erhält automatisch einen \texttt{serverTimestamp()}, und dynamische Abfragen werden als Constraint-Array übergeben \cite{firestore2025}:

\begin{lstlisting}[language=Java, morekeywords={const, await}, caption=Beispielaufruf der generischen Abfragefunktion]
// Alle Produkte einer Kategorie, nach Preis sortiert
const result = await queryDocuments('products',
  [['category', '==', slug]],
  'price'
)
\end{lstlisting}

Auf dieser Basis bauen domänenspezifische Funktionen auf, die zusätzlich Modellinstanziierung und Validierung übernehmen. Die resultierende Schichtung der Anwendung ist in Abbildung~\ref{fig:service-architektur} dargestellt und entspricht dem empfohlenen Service-Layer-Pattern für BaaS-Anwendungen \cite{uunonen2023}.

\section{Benutzerkonten- und Authentifizierungssystem}
\label{sec:authentifizierung}

Das Authentifizierungssystem unterstützt E-Mail-/Passwort-Registrierung sowie Google-Anmeldung via OAuth~2.0 \cite{hardt2012}. Firebase Authentication übernimmt dabei das vollständige Credential-Management inklusive JWT-Ausstellung und automatischer Token-Erneuerung \cite{firebaseAuth2025, bucko2023}.

Für beide Methoden wird ein \textit{Dual-Write-Pattern} angewendet: Authentifizierungsdaten verbleiben in Firebase Auth, während Profilinformationen (Anzeigename, Adresse, Systemrolle) in einem korrespondierenden Dokument der Firestore-Collection \texttt{users} persistiert werden. Diese Trennung ermöglicht beliebige Profilerweiterungen ohne Einschränkungen durch das Firebase-Auth-Schema \cite{milojkovic2024}.

Der globale Route Guard löst eine potenzielle Race Condition zwischen Seitenaufruf und asynchroner Auth-Initialisierung durch eine einmalig abonnierte Promise auf, die den Auth-State abwartet, bevor die Navigationsentscheidung getroffen wird \cite{vuejs2025}:

\begin{lstlisting}[language=Java, morekeywords={const, async, await, return, new, if}, caption=Route Guard mit Auth-Initialisierung und RBAC-Prüfung]
const waitForAuthInit = () => new Promise(resolve => {
  const unsub = onAuthStateChanged(auth, user => { unsub(); resolve(user) })
})

router.beforeEach(async (to, _, next) => {
  const user = await waitForAuthInit()
  if (to.meta.requiresAuth  && !user)              return next('/login')
  if (to.meta.requiresAdmin && !await isAdmin(user)) return next('/')
  next()
})
\end{lstlisting}

Die Administratorrolle ist als \texttt{role: 'admin'} im Firestore-Benutzerdokument gespeichert und wird über \texttt{isAdmin()} im \texttt{User}-Modell ausgewertet. Der Zugriffsschutz erfolgt zweistufig -- clientseitig durch den Router Guard, serverseitig durch Firestore Security Rules -- und realisiert damit das \textit{Defense-in-Depth}-Prinzip \cite{fredj2020}. Abbildung~\ref{fig:auth-flow} stellt beide Abläufe -- Anmeldung und Navigation -- gegenüber.

\section{Produktkatalog und Such-/Filterfunktion}
\label{sec:produktkatalog}

Produkte werden als Instanzen der \texttt{Product}-Modellklasse verwaltet. Vor jedem Schreibvorgang prüft \texttt{validate()} Pflichtfelder und Wertebereichsbedingungen; nur bei positivem Ergebnis wird \texttt{createDocument()} aufgerufen. Das Kapseln von Validierungslogik im Modell verhindert inkonsistente Datenbankzustände und entspricht dem Prinzip der Verantwortlichkeitstrennung \cite{kesavan2023}.

Kategoriefilterung erfolgt serverseitig über Firestore-\texttt{where()}-Constraints, die direkt auf dem Datenbankindex ausgeführt werden. Die Freitextsuche ist hingegen client-seitig implementiert: Produktname und Beschreibung werden lokal geprüft. Dieser Ansatz ist für den vorliegenden Katalogsumfang ausreichend, skaliert jedoch nicht für sehr große Sortimente -- eine bekannte Limitation client-seitiger Suchimplementierungen gegenüber dedizierten Indizierungsdiensten \cite{kothapalli2022}.

\section{Warenkorb und Bestellprozess}
\label{sec:warenkorb}

Die Warenkorbverwaltung basiert auf einem Pinia-Store, der reaktive Referenzen auf Artikel und Gesamtanzahl komponentenübergreifend bereitstellt. Pinia ist die offizielle State-Management-Lösung für Vue~3 und löst das ältere Vuex durch eine leichtgewichtige, Composition-API-basierte API ab \cite{pinia2025}.

Nicht-angemeldete Nutzer erhalten einen cookie-basierten Gast-Warenkorb. Bei der Anmeldung führt \texttt{mergeGuestCart()} eine verlustfreie Zusammenführung durch: Vorhandene Mengen werden addiert, neue Artikel übernommen; der Cookie wird anschließend bereinigt:

\begin{lstlisting}[language=Java, morekeywords={const, if, forEach}, caption=Kern der Warenkorb-Zusammenführung beim Login]
guestCart.forEach(item => {
  const existing = userCart.find(i => i.productId === item.productId)
  if (existing) existing.quantity += item.quantity
  else          userCart.push(item)
})
\end{lstlisting}

Der Checkout-Prozess ist dreistufig: Adresseingabe, Bestellübersicht und Bestätigung. Bei Abschluss wird ein \texttt{Order}-Dokument in Firestore angelegt. Eine strukturierte Checkout-Führung reduziert nachweislich Kaufabbrüche \cite{butnampetch2020}. Den resultierenden Status-Lifecycle zeigt Abbildung~\ref{fig:order-lifecycle}.

\section{Angebots- und Rabattsystem}
\label{sec:angebotssystem}

Das \texttt{Offer}-Modell bildet zeitlich begrenzte Rabattaktionen ab. Die Methode \texttt{isActive()} vergleicht \texttt{startDate} und \texttt{endDate} mit dem aktuellen Zeitstempel; fehlende Felder gelten als unbegrenzt. Der Rabatt wird prozentual über \texttt{discountPercentage} auf den Listenpreis angewendet und bereits beim Laden des Warenkorbs in den \texttt{finalPrice} eingerechnet.

Das System wird durch zwei Cloud Functions ergänzt: \texttt{weeklyOffers.js} versendet wöchentlich per \texttt{pubsub.schedule}-Trigger einen Newsletter mit aktiven Angeboten an abonnierte Nutzer. \texttt{orderStatusChanged.js} reagiert ereignisgesteuert auf Bestellstatusänderungen und benachrichtigt Kunden automatisch per E-Mail. Beide Funktionen illustrieren das Event-Driven-Muster serverloser Architekturen, bei dem Logik auf Datenbankereignisse reagiert statt direkt aufgerufen zu werden \cite{thatikonda2023, firebase2025}.

\section{Administrationsoberfläche}
\label{sec:admin}

Der Administrationsbereich (\texttt{/admin/*}) ist zweistufig abgesichert: Der Vue-Router-Guard prüft \texttt{isAdmin()} auf Clientseite, Firestore Security Rules erzwingen dieselbe Bedingung serverseitig. Diese Redundanz eliminiert den Single Point of Failure, der bei rein clientseitigem Schutz entstünde \cite{fredj2020}.

Der Bereich umfasst fünf Module (Produkte, Kategorien, Bestellungen, Nutzer, Angebote) als eigenständige Views mit vollständigen CRUD-Operationen. Drei wiederverwendbare Komponenten -- \texttt{AdminFilters}, \texttt{AdminTablePagination} und \texttt{AdminPageHeader} -- gewährleisten ein konsistentes UI-Muster und vermeiden Codeduplizierung \cite{kothapalli2021}. Statusänderungen an Bestellungen lösen über \texttt{orderStatusChanged.js} automatische Kundenbenachrichtigungen aus und entkoppeln die UI-Aktion von der Benachrichtigungslogik \cite{milojkovic2024}.
